Troubleshoot with RangerAI — Intelligent Job Diagnostics

2025 · REDWOOD RUNMYJOBS 2026 · PRODUCTION · MODERN UI

In complex distributed systems, identifying why a job failed is a needle-in-a-haystack problem. Developers used to sift through massive raw logs, jump across screens, and hypothesise fixes. Every minute of MTTR is a minute the business runs degraded. So I built an LLM-powered diagnostic overlay that turns raw error logs into actionable intelligence — directly inside the monitoring UI.

65%
Reduction in debugging time
Auto
Log parsing & targeting
1-Click
Diagnostic workflow

my approach

  • Contextual triggering — the prompt layer only activates when a Job enters a terminal Error state, so no noise, just signal.
  • Targeted diagnostics — focused the AI on the stderror.txt stream to isolate the actual failure point.
  • Tri-fold output — raw evidence (logs), plain-English explanation, proposed remedy. All in one overlay.
  • Portability — export AI insights directly to Jira tickets and post-mortems.

what's actually under the hood

  • LLM pipeline — fine-tuned GPT-4o-class model optimised for stack traces and proprietary error codes.
  • Log extraction engine — fetches stderror.txt from AWS S3 only when requested to minimise data egress.
  • Prompt engineering — few-shot prompting with structured JSON output.
  • Conditional UI — React validates job type and file availability before rendering the entry point.

what i actually did (vs the team)

  • Defined the end-to-end architecture from Error-status trigger to the troubleshooting overlay.
  • Iterated system prompts to stop the AI hallucinating fixes for ambiguous hardware failures.
  • Built the API bridge between the Monitoring UI and the LLM inference endpoint.
  • Wrote the Download logic and graceful fallback for missing error logs.

MCP Server — Natural Language Job Operations

2025 · REDWOOD RUNMYJOBS 2026 · MODEL CONTEXT PROTOCOL · AUTOMATION

Operations teams context-switch between terminal and UI — job submission, status checks, and cancellations demand jumping between tools. I architected a stateless MCP proxy bridge that exposes core RunMyJobs operations through natural language, eliminating context-switching friction and letting operators work directly in their LLM client or terminal.

70%
Reduction in data transfer costs
Multi-tenant
Single regional deployment
90%
Faster job operations

my approach

  • Stateless proxy pattern — no credential persistence. Client API keys pass directly to RunMyJobs backend for simplified security.
  • Header-based multi-tenant routing — single regional deployment routes requests via X-RMJ-Instance-ID header.
  • MCP tool set — four core operations exposed: submit_job, get_job, cancel_job, get_process_server.
  • Natural language interface — operators work in terminal or LLM client with zero context-switching.

what's actually under the hood

  • Spring AI MCP framework — bridges MCP protocol to RunMyJobs REST APIs.
  • AWS EKS + Karpenter — co-located in same VPC and region with horizontal pod autoscaling.
  • ALB + WAF ingress layer — protects the MCP server from external threats.
  • Passthrough authentication — client API key relayed directly to backend; zero secrets stored in MCP layer.

what i actually did

  • Architected the stateless proxy pattern and multi-tenant routing strategy.
  • Implemented passthrough auth — eliminated credential storage, direct API key relay to backend.
  • Led integration of the four MVP operations into the Spring AI MCP framework.
  • Designed deployment strategy for co-location in same AWS region/VPC to eliminate egress costs and latency.

§04.5 // building at scale

Leading high-performing teams.

Solo engineer to Sr. development manager: scaling teams, hiring bars, and how technical leadership compounds into organisational impact.

scaling

30+ engineers, SAP Premium Certification

At Redwood, I inherited a mid-sized engineering org and scaled it to 30+ full-stack engineers across AI, platform, and infrastructure. Restructured for autonomy — small squads owning end-to-end from product spec to production monitoring. Result: Gartner Magic Quadrant 2025 recognition, SAP Premium Certification secured in 3 months, 4 major AI features shipped on schedule.

org structure became repeatable pattern

what restructuring actually meant

  • Squad autonomy — Each squad (AI, Platform, Infrastructure) owned their roadmap, deploys, and on-call rotations. No bottleneck at my desk.
  • Clear ownership — Feature requests routed directly to squad leads; conflicts resolved in squad sync rather than escalated.
  • Repeatable hiring — Every hire into a squad model strengthened the pattern. Squad leads became hiring managers. Culture scaled.

how this led to gartner

  • Small squads could move fast on RangerAI features. No dependency hell.
  • SAP cert required deep integration work + customer success stories. Squad autonomy meant SMEs could own the entire customer relationship.
  • Cross-squad collaboration on AI infra happened at squad-lead level, not my mandate.
hiring

The hiring bar: deep technical + collaborative energy

Built a hiring rubric that optimised for senior individual contributors who thrive in small teams. Screened for: strong signal on system design, LLM/AI concepts, proven track record shipping complexity. 82% hiring success rate (new hires still here or promoted). Rejected "brilliant jerks" — collaboration tax outweighed individual brilliance.

quality > quantity. always.

the rubric

  • System design depth — Can they reason about trade-offs (latency vs consistency, cost vs perf)? Do they ask good questions?
  • LLM/AI signal — Not an LLM researcher, but: can they explain RAG? Understand hallucination? Talk about eval strategy?
  • Shipping scars — Have they shipped something hard? What broke? How did they debug it? (Process matters more than perfection.)
  • Collaboration fit — Would they pair well with the squad they're joining? Ego check: can they learn from peers?

82% success means

  • Of 11 hires, 9 are still here or promoted into leadership. 2 left for roles they genuinely wanted (founder tracks, expert-only paths).
  • Zero surprise underperformers. We caught the signal in interviews.
  • Team chemistry stayed high — no "brilliant jerk" sabotage.
mentorship

From IC to manager — 4 promotions in 2 years

Deliberately grew 4 senior engineers into engineering managers and tech leads — 90% internal promotion rate for leadership roles. Monthly 1-on-1s with explicit "here's what a staff-level engineer needs" playbook. Sponsored them into high-visibility projects (Gartner work, AI architecture decisions). Three of them are still in leadership; one transitioned to principal architect.

your career is your responsibility; my job is to show the path

the playbook

  • Month 1-2 — Identify signals: who asks great questions in meetings? Who mentors junior devs without being asked?
  • Month 3-6 — Give them high-visibility projects. Not busy work — real decisions with org impact.
  • Month 7-12 — Monthly 1-on-1s: "Here's what a staff-level engineer looks like. You're doing X. Here's Y you need to develop." Explicit.
  • Month 13+ — Sponsor them into a leadership opportunity (tech lead for a squad, engineering manager for a sub-team).

track record

  • 4 engineers identified → 4 promoted to manager/tech lead within 2 years.
  • 3 of those 4 are still in leadership roles. 1 transitioned to Principal Architect (wanted deep technical track, not people management).
  • Zero regrets. They earned it. They stayed.

Low churn, high growth — the outcome

Org maintained 95%+ retention across 2.5 years (industry average: 80%). When people did leave, it was for founder-level roles or deep expert tracks they couldn't pursue here — not because they were unhappy. Zero involuntary exits — people weren't pushed out, they were grown, promoted, or moved to better fits.

retention is a leading indicator of culture

why people stayed

  • Growth path was obvious — You could see the promotion pipeline. ICs → Leads → Managers. Transparent.
  • Work was meaningful — Gartner, Certification, shipping features millions used. Not busywork.
  • Autonomy existed — Squad owned decisions. Not micromanaged.

cross-team

Connecting silos: engineering + product + security

Engineering didn't own AI strategy in isolation. Built weekly strategy sessions with Product, Security, Infra,Support — unified vision on feature prioritisation, risk gates, infrastructure constraints. Result: no rework cycles where engineering shipped something and product pushed back. 30% faster time-to-market because decisions happened at the intersection.

org structure determines outcomes

the weekly syncs

  • Product leadership — Early visibility into AI roadmap, feature definitions, user stories, customer feedback.
  • Security architects — Real-time risk assessment on LLM ingress/egress, data privacy, compliance. No surprises at audit time.
  • Infrastructure leads — Cloud cost forecasting, compute availability, API rate limits, monitoring strategy.
  • Support/Customer Success — Direct feedback loop on user pain points, common issues, feature requests.

the impact

  • No late-stage feature cuts — All stakeholders aligned from ideation to ship.
  • Faster issue resolution — Support knew who to ping on which team for specific bugs.
  • Holistic risk management — Security got a seat at the table early, not as a gate.
technical debt

The "50-20-30" rule: shipping smart

Enforced a budgeting model: 50% new features, 20% tech debt reduction, 30% operational load (on-call, support, compliance). This prevented the classic burnout trap where engineering drowns in operational work. Tech debt got addressed with intention. New features got room to breathe. The org stayed healthy and predictable.

burnout isn't a badge. it's a management failure.

the budget model in practice

  • 50% new features — This was sacred. No exceptions. It kept product/engineering aligned on innovation.
  • 20% tech debt — Dedicated sprint capacity. Engineers chose their own debt to tackle, fostering ownership.
  • 30% operational load — On-call rotation, support escalations, compliance work, small bug fixes. Guarded fiercely.

impact on burnout

  • Predictable cycles. Engineers knew when they'd be building vs. paying down debt vs. operational.
  • Sense of control. Not just reacting to emergencies, but proactively improving the system.
  • No one felt like they were drowning. Workload was balanced.
