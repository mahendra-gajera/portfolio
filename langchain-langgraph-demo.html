LangChain & LangGraph, explained.

— two libraries. one rules them both, the other lets them argue.

Most production AI agents in 2026 are built with one of these two libraries — and engineers regularly pick the wrong one. LangChain is a pipeline: data flows in one direction through composable steps. LangGraph is a state machine: nodes that can loop, branch, and revisit each other based on conditions. Below: side-by-side, live visualizations, real code, and a decision matrix for when to use which.

the two

Pipeline vs state machine.

Both come from the LangChain team. They solve different shapes of problem. The simplest mental model: LangChain is a Unix pipe, LangGraph is a flowchart with memory.

// LangChain

The pipeline

A linear chain of operations — Prompt → LLM → Output Parser → Result. Data flows one way. Each step transforms the output of the previous. Composable with the | operator (LCEL — LangChain Expression Language).

  • Best for: RAG, summarisation, classification, content generation
  • Strengths: simple, fast to build, easy to test, parallelisable, streaming-first
  • Weakness: no loops, no conditional branching, no shared mutable state
  • Mental model: cat input | llm | parse
// LangGraph

The state machine

A graph of nodes connected by edges. Each node reads and writes a shared state object. Conditional edges decide where to go next based on that state. Built for cycles — agents that loop until they're done.

  • Best for: ReAct agents, multi-agent systems, human-in-the-loop, planner-executor
  • Strengths: loops, branches, persistent state, checkpointing, time-travel debugging
  • Weakness: more setup, harder to reason about, easier to write infinite loops
  • Mental model: a flowchart with memory

the code

# LangChain RAG pipeline — built with LCEL (LangChain Expression Language)
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_community.vectorstores import FAISS
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

# 1. set up the components
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = FAISS.from_texts(docs, embeddings)
retriever   = vectorstore.as_retriever(search_kwargs={"k": 3})
llm         = ChatOpenAI(model="gpt-4o-mini", temperature=0)

prompt = ChatPromptTemplate.from_template("""
Answer the question based only on this context:
{context}

Question: {question}
""")

# 2. compose them with the | operator (LCEL)
chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)

# 3. invoke (or stream, or batch — all free)
answer = chain.invoke("What is RAGAS and what does it measure?")

# streaming — token by token, no extra setup
for chunk in chain.stream("What is RAGAS?"):
    print(chunk, end="", flush=True)
what to notice

The | operator isn't magic — it's function composition. Each component is a Runnable and | chains them. You get streaming, async, batching, and .with_retry() for free. The chain is declarative — it describes the data flow, doesn't execute imperatively.

the code

# LangGraph ReAct agent — built from primitives
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

# 1. define the shared state — what every node reads/writes
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]   # reducer: append
    iterations: int

# 2. define the tools the agent can call
@tool
def multiply(a: int, b: int) -> int:
    """Multiply two integers."""
    return a * b

@tool
def company_founded(name: str) -> int:
    """Return the year a company was founded."""
    return {"Redwood": 1993}.get(name, 0)

tools = [multiply, company_founded]
llm = ChatOpenAI(model="gpt-4o-mini").bind_tools(tools)

# 3. nodes: each is just a function (state) -> partial state update
def agent_node(state: AgentState):
    response = llm.invoke(state["messages"])
    return {"messages": [response], "iterations": state["iterations"] + 1}

def tool_node(state: AgentState):
    last = state["messages"][-1]
    results = []
    for call in last.tool_calls:
        fn = {"multiply": multiply, "company_founded": company_founded}[call["name"]]
        out = fn.invoke(call["args"])
        results.append({"role": "tool", "content": str(out),
                        "tool_call_id": call["id"]})
    return {"messages": results}

# 4. the conditional edge — decides where to go after agent_node
def should_continue(state: AgentState) -> str:
    last = state["messages"][-1]
    if last.tool_calls:
        return "tools"     # loop back through the tools node
    return END             # done — return final answer

# 5. wire the graph
graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)
graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")   # the loop

app = graph.compile()
result = app.invoke({"messages": [("user", "47 × 89 + Redwood founded year")],
                      "iterations": 0})
what to notice

The should_continue function is the heart of a ReAct agent — it inspects the last message and decides: are there more tools to call, or are we done? The tools → agent edge creates the loop. State accumulates through add_messages — a reducer that appends instead of overwriting. Compare this to a LangChain pipeline: it could never loop back on itself.

decision matrix

When to use which.

Most teams default to LangChain and outgrow it. A few default to LangGraph and over-engineer. Here's the rule of thumb I use day to day.

You're building… Why Pick
RAG pipeline — retrieve docs, answer question Linear data flow, no branching, no loops. LangChain's LCEL is exactly the right tool — and you get streaming free. LangChain
Summarisation, classification, extraction One pass, one shape. No state to maintain. Use LCEL. LangChain
ReAct agent — LLM calls tools until done Loops by definition. Needs the agent ↔ tool back-and-forth that only a graph cleanly expresses. LangGraph
Multi-agent system — researcher, coder, reviewer Each agent is a node. Edges encode "who hands off to whom." State is the shared workspace. LangGraph
Human-in-the-loop approval flows Pause for human input, resume from checkpoint. LangGraph's persistence layer is built for this. LangGraph
Planner-executor — plan first, then execute steps Two-phase, with the planner re-invoked if execution fails. Needs conditional branching and retry loops. LangGraph
RAG with conditional re-ranking The pipeline part is LangChain; if you need to retry retrieval based on confidence, wrap it in a LangGraph node. Both
Production deploy with retries, timeouts, observability Both ship with these. LangSmith traces work for both. LangGraph adds checkpointing. Both
production rule

Start with LangChain. Reach for LangGraph the moment you write "if X, retry" or "loop until done". If you're nesting if statements around a chain to fake conditional flow, that's the signal — you've grown out of the pipeline shape.

the rangerai connection

How I used both at Redwood.

The four RangerAI features in RunMyJobs 2026 don't all use the same architecture — and that's intentional. Different shapes of problem, different tools.

// LangChain shape

Product Assistant & Troubleshoot

Both are linear RAG pipelines. Question → retrieve → prompt → LLM → answer. No loops, no agent decision-making — just grounded, fast, streaming responses. Wrapped in a session-memory layer, but the underlying flow is LCEL-style.

  • Why pipeline: deterministic, low-latency, streaming, simple to evaluate
  • Eval: RAGAS faithfulness + answer relevancy on the retrieval output
// LangGraph shape

Automation Co-pilot & Generate

Both are multi-turn agents. Co-pilot iterates on a script with the user — generate, review, refine, retry. Generate ingests a workflow graph, decides which subtree to summarise, sometimes loops back for missing context. Pure pipelines couldn't do either.

  • Why state machine: multi-turn conversation, retry-on-fail, context-window guards
  • Eval: RAGAS over the Golden Script Set as a quality gate at the graph boundary
