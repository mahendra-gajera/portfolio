💡 The Real Question

You've built your AI app. Now where do you run it? Lambda's fast but has limits. ECS scales but needs babysitting. Kubernetes is bulletproof but expensive to operate. SageMaker handles GPUs but locks you in.

This guide is the framework I actually use to decide. No vendor pitches — just tradeoffs from real deployments at Microsoft, LSEG, JPMC, DBS Bank.

⚡ Rule of thumb: Pick the simplest deployment that handles your load. You can always upgrade. Starting with Kubernetes for a side project is how you end up debugging YAML instead of shipping features.

🏗 Reference Architecture: Production AI App PRACTICAL

What a real production AI deployment looks like. This is roughly what I'd build for a typical RAG/agent app — boring, battle-tested, the kind of architecture that survives real traffic.

→ Production AI request flow
⚡ Why this design? API Gateway gives you rate limiting and auth without code. Lambda is cheap and scales infinitely for thin orchestration. The vector store and LLM are managed services — you don't run the hard parts. The Redis cache is the secret weapon: 30-70% of LLM calls in production can be served from cache.
// Production deployment with AWS CDK (TypeScript)
import * as cdk from 'aws-cdk-lib'; import * as lambda from 'aws-cdk-lib/aws-lambda'; import * as apigw from 'aws-cdk-lib/aws-apigateway'; export class AiAppStack extends cdk.Stack { constructor(scope, id, props) { super(scope, id, props); // 1. The orchestration Lambda — calls Bedrock, manages RAG const ragFn = new lambda.Function(this, 'RagHandler', { runtime: lambda.Runtime.PYTHON_3_12, handler: 'index.handler', code: lambda.Code.fromAsset('lambda/rag'), memorySize: 1024, timeout: cdk.Duration.seconds(30), environment: { BEDROCK_MODEL_ID: 'anthropic.claude-sonnet-4-6', VECTOR_STORE_URL: vectorStore.url, CACHE_URL: redisCluster.endpoint, }, }); // 2. API Gateway — rate limiting, auth, throttling const api = new apigw.RestApi(this, 'AiApi', { throttle: { rateLimit: 100, burstLimit: 200 }, }); api.root.addMethod('POST', new apigw.LambdaIntegration(ragFn)); // 3. Grant Bedrock access ragFn.addToRolePolicy(new iam.PolicyStatement({ actions: ['bedrock:InvokeModel'], resources: ['arn:aws:bedrock:*::foundation-model/anthropic.*'], })); } }
// The Lambda handler itself
import os, json, boto3, redis from langchain_aws import ChatBedrock bedrock = boto3.client('bedrock-runtime') cache = redis.Redis.from_url(os.environ['CACHE_URL']) llm = ChatBedrock(model_id=os.environ['BEDROCK_MODEL_ID']) def handler(event, context): query = json.loads(event['body'])['query'] # 1. Check cache first — saves 30-70% of LLM costs cached = cache.get(cache_key(query)) if cached: return {'statusCode': 200, 'body': cached} # 2. RAG: retrieve from vector store docs = vector_store.similarity_search(query, k=5) # 3. Augment + generate response = llm.invoke(build_prompt(query, docs)) # 4. Cache for next time (5 min TTL) cache.setex(cache_key(query), 300, response.content) return {'statusCode': 200, 'body': response.content}
✅ Why this scales: Lambda auto-scales to thousands of concurrent invocations. Bedrock handles model scaling. Redis is the only thing you sized — and it's cheap. Your scaling problem becomes someone else's scaling problem.

⚡ The big insight: For most AI apps, your LLM API costs (Bedrock, OpenAI) dwarf your compute costs. Optimizing compute when LLM tokens are 90% of your bill is fixing the wrong problem. Cache aggressively. Use cheaper models where you can. Then worry about compute.
⚠️ Hidden costs nobody mentions:
• NAT Gateway — Lambdas in VPCs need this. ~$32/mo + per-GB egress.
• Data transfer — Cross-AZ traffic = $0.01/GB. Adds up at scale.
• CloudWatch logs — Verbose logging from Lambdas can cost more than the Lambdas.
• Idle endpoints — SageMaker endpoints, ALBs, NAT Gateways all bill 24/7.
• Reserved capacity — Provisioned concurrency on Lambda kills the "scale to zero" benefit.

📋 Real-World Use Cases PATTERNS

Common AI deployment scenarios with picks and reasoning.

💬 Internal chatbot (calls OpenAI API)
AWS Lambda + API Gateway
Low complexity, bursty traffic (employees use it during work hours, idle otherwise). Lambda's scale-to-zero is perfect. Cold starts of 1-2 sec are acceptable for chat. ~$30/mo at typical scale.
🌐 Customer-facing RAG app (100K+ req/day)
ECS Fargate+ Bedrock
Steady production load — Lambda costs more than containers at this volume. Fargate keeps containers warm (no cold starts), auto-scales horizontally, integrates with ALB for routing. Use Bedrock for the LLM so you skip model ops.
🧠 Self-hosted Llama 3.3 70B inference
Modal / Beamor K8s + vLLM
Need GPUs but want to skip DevOps? Modal. Have a platform team and need cost control at scale? K8s with vLLM for high-throughput serving. Avoid SageMaker unless you need its fine-tuning features.
📊 Batch document processing (millions of docs)
Lambda + SQS+ Bedrock Batch
Async, parallel, fault-tolerant. Lambdas pull from SQS queue, hit Bedrock Batch API for 50% discount. No need for always-on compute. Scales to millions overnight then bills $0 the rest of the time.
🤖 Multi-agent workflow with long-running steps
ECSor K8s
Agents can run 30+ seconds. Lambda's 15-min limit is fine, but stateful coordination across agents is awkward. Containers let you keep state in-process. Use Step Functions or Temporal for orchestration.
🏥 Regulated industry (HIPAA, financial)
EKS + BedrockPrivateLink
EKS gives you network isolation (PrivateLink, VPC endpoints, no internet). Bedrock has BAA and HIPAA eligibility. Lambda complicates audit trails for some compliance frameworks. This is what I deployed at LSEG for trading workflows.
🎯 Real-time AI in mobile/web app (<500ms)
ECS Fargate + ALB
Lambda cold starts of 1-3 seconds kill strict latency SLAs. Keep containers warm. Use Bedrock or OpenAI streaming for token-by-token response — perceived latency drops dramatically. Add CloudFront for global edge.
🔬 ML training / fine-tuning runs
SageMaker Trainingor RunPod
SageMaker for managed experience with experiment tracking and hyperparameter tuning. RunPod for 60% cheaper GPU when you don't need the bells and whistles. Avoid running training on your production infra.
🚀 Side project / MVP
Lambda + Vercelor Modal for GPU
Don't over-engineer. Lambda for backend ($0 idle), Vercel for frontend, OpenAI/Claude API for the AI part. Total infra cost: probably $5-20/mo until you hit real scale. Worry about K8s after you have users.

📐 Production Rules I Follow REAL TALK

Hard-won lessons from deploying AI at Microsoft, LSEG, JPMC, DBS Bank. Patterns that survived real incidents.

📏 Rule 1 — Cache before you scale

In production RAG, 30-70% of queries are repeats. Add Redis with a 5-min TTL on (query → response). This saves more money than any infra optimization. Cost: ~$15/mo for a small Redis. Savings: thousands.
def cached_llm_call(query): key = hashlib.sha256(query.encode()).hexdigest() if cached := redis.get(key): return cached # 30-70% of calls end here response = llm.invoke(query) redis.setex(key, 300, response) # 5 min TTL return response

📏 Rule 2 — Streaming > waiting

A 5-second response feels broken. The same 5-second response streamed token-by-token feels instant. Use SSE (Server-Sent Events) or WebSockets. ALB supports streaming; API Gateway has Lambda response streaming since 2023.

📏 Rule 3 — Async by default

If a request can take >10 seconds, don't block the user. Return a job ID immediately, do work in the background (SQS + Lambda or Step Functions), poll or push completion. This is how every serious AI app handles long-running work.

📏 Rule 4 — Cold starts are a UX bug

Lambda Python cold starts are 1-3 sec. For interactive apps that's noticeable. Three fixes: (1) provisioned concurrency, (2) keep functions warm with EventBridge ping, (3) use ECS Fargate where it matters. Profile before optimizing.

📏 Rule 5 — Pick your bottleneck

Your latency is dominated by one thing: usually the LLM call itself. Optimizing your container start time when the LLM takes 3 seconds is wasted effort. Profile, find the bottleneck, fix that.

📏 Rule 6 — Observability isn't optional

From day one: log every prompt, every response, every tool call, every error. Track p50/p95/p99 latency, token usage, cost per request. Use OpenTelemetry, Datadog, Grafana — whatever your team uses. You can't fix what you don't measure.
from opentelemetry import trace tracer = trace.get_tracer(__name__) with tracer.start_as_current_span("llm_call") as span: span.set_attribute("model", "claude-sonnet") span.set_attribute("prompt_tokens", count_tokens(prompt)) response = llm.invoke(prompt) span.set_attribute("output_tokens", response.usage.output_tokens) span.set_attribute("cost_usd", estimate_cost(response))

📏 Rule 7 — Plan for failure modes

LLMs go down. APIs rate-limit. Models get deprecated. Build for it. Wrap every LLM call in retries with exponential backoff. Have a fallback model (Bedrock if Anthropic API fails, vice versa). Graceful degradation > 500 errors.

📏 Rule 8 — IaC from day one

Terraform, CDK, Pulumi — pick one. Click-Ops deployments are landmines. Yes, this is more upfront work. Yes, it pays off the third time you need to recreate the stack at 3 AM after someone deleted something.

📏 Rule 9 — Start managed, go custom when it hurts

Start with Bedrock or OpenAI API. Move to self-hosted only when (a) costs blow up, (b) latency is unfixable, or (c) compliance demands it. Most teams self-host too early and regret it. The OpenAI bill that justifies a 10-engineer ML platform team is enormous.
⚠️ The thing that will hurt the most: You'll be tempted to over-engineer for scale you don't have yet. Resist. Build the boring thing. Ship. Measure. Scale when reality forces you to. Production wisdom is mostly knowing what NOT to build.
✅ The framework one more time:
• API-only + low traffic → Lambda
• API-only + high traffic → ECS Fargate
• Self-host + bursty → Modal/Beam
• Self-host + steady → Kubernetes + vLLM
• Regulated → EKS + Bedrock/Azure OpenAI
• Training → SageMaker or RunPod
• MVP → Lambda + Vercel + OpenAI
